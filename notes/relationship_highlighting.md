# Highlighting one relationship type at a time in a saved analysis

Neel's request: a new marimo notebook that reads in a saved analysis, offers an alphabetically sorted menu of every relationship type actually attested in the passage, and -- when the user picks one -- shows the passage's own verbal-unit-colored HTML with that relationship's edges marked: the start (source) token of each edge underlined, the end (target) token boxed in a rounded rectangle ("circled," per the request, drawn as a box so it fits words of any length rather than literally a circle). Hovering over a marked token shows `start - relationship - end` for every edge of *that* relationship touching it -- and only that relationship, even when the same token has other relations too.

## New library API (`arsgrammatica/rendering.py`)

Three new public functions/one dataclass, exported from `arsgrammatica/__init__.py` alongside the existing rendering functions:

- **`RelationshipEdge`** -- `start_id`/`start_label`, `end_id`/`end_label`, `relationship`. `end_id` is `None` in two cases (both still get a real `end_label` for a tooltip): the virtual `"root"` node every independent verb's `unit verb` edge points to (same convention `tokengraph_to_mermaid()`/`tokengraph_to_dot()` already use), and a `relatedtoken1`/`2` value that doesn't resolve to any id actually in the tokengraph (a broken/incomplete analysis -- also reported as a warning, mirroring `tokengraph_to_mermaid()`'s own "skipped edge ... not in tokengraph" warning for the same situation).
- **`tokengraph_relationship_types(tokengraph) -> List[str]`** -- every distinct value across every token's `relationship1`/`relationship2`, deduplicated and alphabetically sorted. This is the menu.
- **`relationship_edges(tokengraph, relationship=None) -> (List[RelationshipEdge], List[str])`** -- every edge (or just the ones matching `relationship`), walking `relatedtoken1`/`relationship1` then `relatedtoken2`/`relationship2` for each token -- the identical iteration `tokengraph_to_mermaid()` uses for its own arrows, so "start" and "end" here agree with that diagram's arrow direction (subordinate -> governing).
- **`tokengraph_to_relationship_html(tokengraph, relationship=None) -> (str, List[str])`** -- same output as `tokengraph_to_html()` (verbal-unit background colors, spacing/escaping/quote-pairing) plus, when `relationship` is given: `ag-rel-start` (underline) on every edge's start token, `ag-rel-end` (rounded-rect border) on every edge's end token, and a native HTML `title` attribute on each listing only the matching edges touching it, one per line. `relationship=None` (the default) marks nothing -- byte-identical to `tokengraph_to_html()`'s own output, plus a small `<style>` block bundled at the front so the returned string is self-contained (safe to drop into a notebook cell alone, harmless if that CSS ends up duplicated across cells).

**No JavaScript anywhere.** Everything -- which tokens get boxed/underlined, what each tooltip says -- is computed in Python and baked into the HTML string fresh each time `relationship` changes. This fits how marimo already works (a UI element's value changing re-runs every cell that depends on it), so the notebook cell that calls `tokengraph_to_relationship_html()` just re-renders on its own whenever the relationship dropdown changes -- no custom event wiring needed.

**The tooltip itself is a CSS-only hover bubble, not the native `title` attribute (fixed 2026-09-25).** The first version relied only on the browser's native `title`-attribute tooltip. That worked fine as a bare standalone page, but Neel reported no hover display at all once the notebook was actually running in marimo -- the highlighting (colors/underline/box) showed up correctly, only the tooltip didn't. Root cause: a native `title` tooltip is the browser's OWN chrome-level popup, and it doesn't reliably fire once the element sits inside a host application's own DOM/output area (a marimo cell's output region here) rather than a page opened on its own -- exactly the "beautiful highlighting, no hover" symptom. Fixed by drawing the tooltip with pure CSS instead: every token that has one gets an `ag-rel-tip` class plus a `data-tooltip="..."` attribute holding the same text, and `.ag-rel-tip:hover::after { content: attr(data-tooltip); ... }` renders it as a small dark bubble positioned above the word -- generated content pulled straight from the DOM attribute, so still zero JavaScript. The native `title` attribute is kept too (redundant, harmless) as an accessibility/fallback aid. Verified visually with a headless-Chromium screenshot (hovering over a real token from a real saved analysis correctly shows its tooltip bubble) as well as with new unit tests asserting the CSS rule and the `data-tooltip`/`title` attributes are both present with identical text.

A token that ends up with no color, no highlight class, and no tooltip is left as plain escaped text with no wrapping `<span>` at all, same as `tokengraph_to_html()` already does for an unassigned token.

## New notebook: `marimo/latin_syntaxer_relationships.py`

Same "no LM access needed" shape as `latin_syntaxer_review.py`: a `file_browser` to pick a saved-analysis file (`read_analyses()`'s own format), a sentence dropdown (`split_analysis_by_sentence()`), then -- new here -- a relationship-type dropdown built from `tokengraph_relationship_types()` for whichever sentence is currently selected, and the highlighted HTML display driven by `tokengraph_to_relationship_html()`. A plain-text preview and a warnings callout (for `relationship_edges()`'s own warnings, when an analysis has a broken/unresolvable relation) round it out. Picking a sentence resets which relationships are even offered (a different sentence attests a different subset); picking `relationship=None` (nothing chosen yet, the dropdown's own default) just shows the plain colored-by-verbal-unit view.

## Addendum 2 (2026-09-25): neutralize non-selected tokens

Same-day follow-up: implemented the "grey out everything except the selected relationship value" idea floated above, once Neel confirmed the typography pass alone (colors still fully on) wasn't what he meant by "non-selected nodes ... not changing to neutral color."

`tokengraph_to_relationship_html()` now flattens a token's ordinary verbal-unit background/text color to a neutral gray (new `_NEUTRAL_FILL = "#e2e2e2"` / `_NEUTRAL_TEXT = "#8a8a8a"` module constants, deliberately outside `verbal_units.py`'s own palette so neutral can never be mistaken for a real clause color) whenever a `relationship` is selected AND that token is NOT one of that relationship's own edge start/end tokens -- computed per-TOKEN, not per-verbal-unit, so a direct object sitting in the very same clause as a highlighted subject still gets neutralized; only the actual selected edges' own endpoints stay lit. This drives off the same `relationship` parameter the notebook's existing dropdown already supplies -- no new UI, exactly as discussed (see the "Not implemented" note this replaces from the first addendum). A token that never had a color in the first place (punctuation, an unassigned token, ...) is untouched either way.

One deliberate refinement over the naive "relationship is not None" reading: selecting a relationship the current sentence doesn't attest at all (e.g. a stale dropdown value left over from a previous sentence) does NOT flatten the whole passage to gray -- that's still the documented "no highlighting, no error" no-op, byte-identical to `relationship=None`. Neutralizing is gated on `bool(edges)` (at least one real match), not just "something is selected," so a non-match reads as "nothing to highlight" rather than a wall of gray that looks broken.

Added three new tests to `tests/test_relationship_highlight.py` (using a new two-independent-clause fixture, `_TWO_CLAUSES_WITH_OBJECT`, with real `verbalunitid`s so it actually gets verbal-unit colors -- unlike the pre-existing `_ARMA_VIRUMQUE_CANO` fixture, which turns out never to get any color at all, having no `verbalunitid` anchor): selecting "subject" keeps both subject edges' own tokens (across BOTH clauses) at full color while neutralizing a same-clause direct object; nothing is neutralized when `relationship=None`; selecting an unattested relationship reproduces `relationship=None`'s output byte-for-byte (no neutralization, no highlighting). Full suite: 1851 passed (1848 + these 3), 2 skipped, 7 deselected -- same scratch-venv-outside-the-repo convention as the typography pass. Also regenerated `Claude outputs/rel_typography_check.html` with genuine before/after output (nothing selected vs. "subject" selected) on that same two-clause fixture, so Neel can see "puellam" go neutral while its clause-mate "videt" stays colored.
